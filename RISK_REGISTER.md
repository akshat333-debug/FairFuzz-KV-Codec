# Risk Register

This document tracks unresolved risks, technical debt, and potential failures in the FairFuzzKV-Codec implementation.

| Risk ID | Description | Impact | Mitigation Strategy | Status |
|---|---|---|---|---|
| R-01 | Overhead of exact byte accounting slows down the evaluation loop | Low | Implement fast C++/CUDA extensions for accounting if Python overhead becomes a bottleneck. Currently keeping it in Python for exactness. | Open |
| R-02 | Model architecture drift | Medium | The capture module must use stable hook points (e.g., HuggingFace `past_key_values` standard). Incident: transformers 5.x replaced `DynamicCache.key_cache`/`.value_cache` with `DynamicCache.layers[i].keys`/`.values`, which silently broke capture (caught only by manual demo run, not CI, since no test exercised a real model). Fixed in `hf_capture.py` with API-version fallback and covered by `tests/cache_capture/test_hf_capture.py`. Future transformers releases can still change this API again. | Open |
| R-03 | Fragility calibration (`fragility_estimation.calibrated_model`) is validated only on a small pilot corpus (~100 surface units from 7 curated sentences). Held-out AUC/Brier numbers are real, measured, and honestly reported (never fabricated), but the sample is far too small to support a "the learned model generalizes" claim. | Medium | Before relying on the calibrated model for real allocation decisions, re-run `fit_and_calibrate` against a much larger, more representative multilingual corpus and re-check `beats_transparent_baseline` holds at scale. | Open |
| R-04 | `rare_token_indicator` uses token-id rank as a rarity proxy (no real corpus-frequency table available); `continuation_ratio` mis-classifies the very first token of an entire sequence as "continuation" since it never carries a leading-space marker even when word-initial. Both are documented heuristics in `fragility_estimation/features.py`, not learned/measured quantities. | Low | Replace with a real frequency table (rare_token) and a position-aware first-token exception (continuation_ratio) if these heuristics prove too coarse in practice. | Open |
| R-05 | `code-review-graph` (external MCP tool) hit repeated `cannot start a transaction within a transaction` SQLite errors when its own MCP server process holds `graph.db` open concurrently with a CLI `build` invocation. Not a FairFuzzKV-Codec code defect - a concurrency limitation of the external tool. | Low | RESOLVED: rebuild via the MCP server's own build tool (same process that holds the lock) instead of the standalone `code-review-graph build` CLI. Graph now clean (67 files, 288 nodes, 1757 edges). Do not run the CLI `build` while an MCP server session is attached to the same repo. | Resolved |
| R-06 | Gate 1 (FragKV-MinPairs causal study, `gate1_study/GATE1_REPORT.md`) came back **WEAK_PASS**, not PASS: the FullKV lossless control itself collapses from 48% to 0% accuracy between n_g=1 and n_g=8, a huge base-model confound that this study cannot cleanly separate from a genuine compression-specific effect. Only TopK50 shows a small (7.5-point), statistically significant, monotonic effect - below the pre-registered "practically meaningful" bar. | High (blocks the fairness/causal narrative) | Do not report "fragmentation causally drives compression failure" as validated. The n_g=4/8 renderings use zero-width-joiner insertion, which may itself be more out-of-distribution than a natural fragmentation signal for a 0.5B base model - a follow-up study should use more natural high-fragmentation renderings and/or a larger model before drawing a stronger conclusion. The codec deliverable (Modules 1-4) does not depend on this claim and is unaffected. | Open |
| R-07 | During Prompt 6 development, `ScalarQuantCodec`'s groupwise granularity initially stored one scale/zero-point value per TENSOR ELEMENT instead of per GROUP (broadcast-expanded values were stored instead of compact ones), inflating INT4-groupwise16 from ~4 bits/element to ~68 bits/element. Caught via a real benchmark run (not by the unit tests, which only checked round-trip correctness, not storage size) before being committed. | Medium (silent - correctness was fine, only accounting was wrong) | Fixed: scale/zero-point are now computed and stored at compact (per-group) resolution, broadcast to full shape only transiently for the quantize/dequantize arithmetic. Added a permanent regression test, `test_groupwise_scale_storage_is_compact_not_per_element`, asserting groupwise bits/element stays below per_channel's. Lesson: round-trip tests alone don't catch storage-accounting bugs - always assert bits/element too. | Resolved |
| R-08 | A second real bug caught during Prompt 6 development: asymmetric (unsigned) 8-bit quantization values in [0, 255] were being force-cast to signed `int8` before packing, silently wrapping any value >=128 negative and producing garbage on dequantization (MSE ~44 instead of ~0.02 in one manual check). | Medium (silent correctness bug, not just accounting) | Fixed: the intermediate quantized tensor now uses `torch.uint8` when `symmetric=False` and `torch.int8` when `symmetric=True`; `pack_int8`/`unpack_int8` no longer force a dtype (previously always coerced to `int8`, which was the actual source of the wraparound). Covered by `tests/quantization/test_packing.py::test_pack_int8_preserves_unsigned_values_without_wraparound` and the full asymmetric parametrization in `test_scalar_quant.py`. | Resolved |
| R-09 | Gate 2 (matched-bit fairness experiment, `gate2_fairness_study/GATE2_REPORT.md`) came back **FAIL** across 6 runs (2 seeds x 3 budgets): the aggregate and minimax allocators selected identical per-cohort bit-widths in every run (zero worst-cohort fairness benefit), and the intersection-full-correct isolation subset retained only the low-fragmentation cohorts (n_g=1,2) because n_g=4/8 have ~0 base-model-correct examples - the same confound as R-06. So the fairness thesis could not even be posed across the intended range. | High (undercuts the Q1 fairness narrative) | Do not report a fairness benefit of minimax over aggregate - Gate 2 is negative evidence at this scale. The codec, LBG, format, pruning, and both allocators are unaffected and preserved. To give the thesis a real test: (a) naturalistic high-fragmentation renderings / larger model so n_g=4,8 survive isolation, and (b) a heterogeneous cohort set whose degradation curves actually diverge so the two allocators produce different allocations; then re-run the unchanged frozen decision logic at scale. | Open |
| R-10 | Gate 4 (fuzzy-vs-simple repair-priority ablation, `GATE4_REPORT.md`) came back **FAIL** on a real Qwen2.5-0.5B pilot (5 groups x 2 seeds x 4 `n_g` x 2 budgets = 80 pooled cells): the Module 3 fuzzy scorer's mean accuracy gain over no-repair was -0.013 (25% directionally consistent, below the 80% consistency bar), it INCREASED mean worst-cohort degradation by 0.050 (an overprotection failure mode - see `GATE4_REPORT.md`'s item-98 notes for a concrete no_repair-correct -> fuzzy-incorrect regression), and its 95% CI vs the best simple competitor ([-0.050, 0.037]) did not exclude domination. | Medium (undercuts the fuzzy-scoring claim, not the codec) | Do not report fuzzy scoring as validated or superior to monotone/knapsack/logistic - Gate 4 is negative evidence at this scale. Per the automatic naming switch (`core/naming.py`), the project is renamed **FragKV-Codec**; the codec (capture, Unicode grouping, fragility estimation, quantization, pruning, allocation, metadata coding, decoder) and all four repair-priority scorers remain in the codebase, unaffected - fuzzy is just not claimed better. To give the thesis a real test: a larger/more heterogeneous candidate pool (naturalistic high-fragmentation text, multiple audited heads/layers, more groups) before re-running the unchanged frozen decision logic at scale. | Open |
| R-11 | `fragkv_minpairs.dataset_card`'s `write_dataset`/`load_dataset` opened files without `encoding="utf-8"`, so on Windows' default `cp1252` locale it crashed writing/reading any text containing a zero-width-joiner or other non-cp1252 character (flagged during Prompt 13 as a pre-existing, out-of-scope bug; it became a hard blocker during Prompt 15 when `run_indiclongcomp_study.py` needed to load `gate1_study/dataset/` for a real contamination self-check). | Medium (blocked a real check, not just cosmetic) | Fixed: `open()`/`read_text()`/`write_text()` calls in `fragkv_minpairs/dataset_card.py` now pass `encoding="utf-8"` explicitly. `indic_longcomp/dataset_card.py` was written with `encoding="utf-8"` from the start (it writes real Devanagari text). Regression-tested: `tests/benchmarks/fragkv_minpairs/test_stats_and_dataset_card.py::test_write_and_load_dataset_round_trips` now passes on Windows; full `tests/benchmarks/fragkv_minpairs/` suite (40 tests) re-run clean after the fix. | Resolved |
| R-12 | IndicLongComp (Prompt 15) course-subset real FullKV run on Qwen2.5-0.5B found the intersection-full-correct isolation subset EMPTY (0/10 groups) - per-language accuracy 0-20% on only 8-10 datapoints per breakdown cell (2 groups/task-family pilot scale). | Low (expected at this sample size, not a benchmark defect) | Too small a sample to distinguish genuine model-capability limits from ordinary small-n noise - FragKV-MinPairs' own real 200-group Gate-1 study found ~48% accuracy on a structurally similar retrieval task, so this is not evidence the benchmark or model is broken. Do not run a compression/fairness comparison on the course subset's isolation subset (it's empty). The 250-group journal subset is generated and structurally validated but has NOT had a real FullKV run (compute budget) - run that next to get an adequately-powered isolation subset. See INDICLONGCOMP_REPORT.md. | Open |
| R-13 | `LBGVectorQuantCodec` self-calibrating (no separate `fit()` call) with `codebook_size=256` and no `minibatch` cap on a REAL Qwen2.5-0.5B-sized K/V tensor (~150k+ vectors at `vector_dim=2`) made the first `run_baseline_matrix.py` attempt (Prompt 16) run for many hours with zero progress output before being killed - LBG's split+Lloyd training cost scales with vector count and codebook size, and self-calibrating fresh on every one of 80 (variant x K/V) calls multiplied that cost badly. | Medium (silently made a real study prohibitively slow, not incorrect) | Fixed: `registry.py`'s `lbg_fixed` factory now passes `minibatch=4096, max_iters=15`, capping per-Lloyd-iteration cost regardless of input tensor size. Verified: a 1-group smoke test that previously would have hung completed in under 30s per variant (LBG calls dropped to ~2-7s each) after the fix; the full 40-variant study then completed in a few minutes. Lesson: any codec that self-calibrates per-call must have its training cost capped (minibatch/max_iters) before being wired into an automated per-example comparison loop, not just tested once on a small synthetic tensor. | Resolved |
| R-14 | A real bug in `baselines/registry.py`'s continuous (binary-searched) adapter factories (`topk_l2`, `snapkv`, `pyramidkv`, `h2o`): each divided its argument by 16.0 as if it were still the outer target bits/element, when `adapter.tune_to_matched_bits`'s binary search actually passes the SEARCHED RETENTION RATIO itself (already in [0.01, 1.0], mirroring `MatchedBitEvaluator.tune_topk`'s `TopKCodec(retention_ratio=mid)` pattern) - the double-division locked every search into a narrow, near-zero ratio band regardless of target, so all four prefill/decode-time adapters landed near ~1.0 bits/element (target 4.0) with 0/40 matched in the first real study run. | Medium (produced a real but silently-wrong result, not a crash) | Fixed: factories now use their argument directly as the ratio. Verified via an isolated realistic-tensor check (24 layers, head_dim=64, seq=100) showing all four adapters landing within 0.5% of the 4.0 bits/element target post-fix, then a full real re-run confirmed 40/40 matched in both the prefill-selection and decode-time-selection regimes. Caught before being reported as a real result - the buggy 0/40-matched output was never treated as the study's answer. | Resolved |
| R-15 | Prompt 17 (Gate 3): the FragKV-MinPairs numeric rendering ladder (`numeric_forms.RENDER_LADDER`), calibrated against Qwen2.5-0.5B's byte-level BPE tokenizer, could not construct ANY valid group under TinyLlama-1.1B's SentencePiece tokenizer using the frozen tolerance `{1:0,2:0,4:1,8:1}` - measured directly: the digit sets that can hit `n_g=4` (`{1,2,6}`) and `n_g=8` (`{0,4,5,9}`) within tolerance are disjoint, so no single digit satisfies both simultaneously. | Medium (blocked the entire cross-model study, not incorrect once found) | Real, transparent, documented recalibration: widened tolerance to `{4:2, 8:2}` for TinyLlama specifically (measured to make 7/10 digits reachable) via a new optional `token_count_tolerance` parameter threaded through `generator.build_group`/`generate_dataset`/`generate_validated_dataset` and `validators.validate_group`/`validate_dataset` (default `None` preserves the frozen Qwen behavior exactly - regression-verified, 40/40 `tests/benchmarks/fragkv_minpairs/` tests unchanged). Side effect noted honestly: with the wider tolerance, `n_g=4` sometimes resolves to the same rendering as `n_g=2` for some digits (the ladder search returns the first rung within tolerance), weakening that specific level's distinctiveness for TinyLlama - reported in GATE3_REPORT.md, not hidden. This is itself the real, measured answer to Prompt 17 item 116 for this specific mechanism: it does NOT transfer without tokenizer-specific recalibration. | Resolved |
